# ChatSense model council

Operating policy dated 24 November 2026. The owner assigned this hierarchy for new work. Issue #23 preserves the former charter and verified delegation history. Scientific, spending, privacy, merge and launch decisions retain their existing approval requirements. This policy adds no background agent, scheduler or vendor integration. [Previous charter and native-harness rules](https://github.com/parthganguly/chatsense/issues/23)

## Routing and decision protocol

Routine, reversible work with clear acceptance criteria goes directly to the lowest-cost capable, verified route. Sol can use a fresh worker with a bounded input packet for work the owner has already authorized. Keep escalation to the decision the worker cannot resolve. The owner authorizes any added scope, spend, release, merge or consequential privacy change.

Convene a council for a consequential scientific interpretation, core architecture choice, product claim or repeated structural failure. Neon frames the human problem and defines the decision. Give Astra, Kimi and Opus the same governing question, frozen facts and their distinct assignments. Astra explores unconventional hypotheses, Kimi builds a competing explanation and Opus forms an independent technical position. Preserve the same source hashes and each full first-pass argument. Keep other positions, coordinator recommendations and expected answers out of the first passes. If a reviewer inherits earlier reasoning, label the review non-blind and limit the claim of independence.

Once independent positions are sealed, compare them directly with the artifacts, counterexamples and disagreements. Opus rules on technical feasibility. Scientific objections stay open until supported evidence resolves them. Neon chairs synthesis and reviews consequential wording, including the limits of the evidence. Sol records facts, tested results, hypotheses, dissent, remaining uncertainty and the authorized next action. Owner-gated actions remain pending. Sonnet or Opus implements authorized work and Terra then verifies the exact candidate on consequential code, experiment runtime/science, privacy/security boundaries, or post-failure repairs. The strength of the evidence determines disposition. A missing reviewer has no imputed vote or approval.

An unavailable route is a scheduling fact. Continue independent authorized work and record the role-specific gate as pending. A publication that requires Neon awaits explicit review of its actual text. Routine factual tracking may record receipt IDs, extant state and blockers while that gate is pending.

## Execution and verification

1. State the objective, working hypothesis, executable task, allowed writes, revision and acceptance tests. Name the stop condition and test input provenance.
2. Use one writer per worktree, sequential dependent steps and separate snapshots or inlined immutable packets for independent readers. Use a native authenticated harness for each named route. Record requested model, harness version, selected or resolved model where exposed, run identity, source and prompt hashes, actual permissions or constraints, exit status, evidence and usage. For any monetary figure, record the billing source, attribution method and period when relevant. Label an API-equivalent estimate, shared allowance use and an attributable settled charge separately. Mark unobservable charges unknown. A catalog entry shows availability for selection. A successful fresh run with its own result and metadata demonstrates invocation.
3. Verify consequential code, experiment runtime or science, privacy/security boundaries, and repairs following a failed invariant independently on the exact candidate. Use negative controls and a fresh regression or independent oracle as appropriate. Record the exact candidate, reviewer and result, any earlier diagnoses or expected results supplied to the reviewer, and whether the review was blind or which independent work was performed despite prior context. A session ID alone proves invocation. Keep the acceptance gate pending when required evidence is unavailable. Keep review and context proportional to the risk. Independent verification of a material follow-up diff may be focused only with recorded evidence that earlier verification still applies; each task must define its escalation boundary.
4. Record the checkpoint or diagnosed failure. Maintain a small revision history with failing property, cause, repair, observed independent result and remaining delta. Timebox retries and use at most two repair attempts per failing invariant before architectural reconsideration with Opus and, where the mechanism is scientific, Astra. Stop earlier for no progress, exhausted resources, unavailable required evidence or an owner decision. A new approval covers a specific new scope and revision.
5. Use brief smoke tasks and modest reasoning effort by default. Use a real assignment as the smoke when it fits. Use higher effort for a defined frontier or adversarial problem. Verify allowance and use no paid fallback, purchases, refills or paid API keys without owner authorization. Pin options, capture one attempt per task, and retry only a diagnosed recoverable infrastructure failure within scope.

Use public or approved synthetic inputs in cross-provider packets. Keep credentials, private exports, user data and raw authorization material outside prompts and published receipts. Review native permissions before dispatch and treat host access, harness restrictions and human trust grants as distinct. Operate through the repository and explicit handoffs. GitHub is the coordination record.
